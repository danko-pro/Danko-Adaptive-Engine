# План внедрения V2/V4 в проект

Этот план описывает, как аккуратно довести систему от текущего состояния V2 к устойчивой адаптации блоков и подготовить будущий V4 Content Engine.

Главная цель: блоки не должны хаотично сжиматься, терять смысл, налезать друг на друга или зависеть от последнего адаптированного состояния. Система должна сохранять авторскую композицию, учитывать роли блоков и уважать минимальные размеры содержимого.

## Текущая база

Уже есть:

- V1 / Geometry Engine: сетка, координаты, операции, границы, коллизии.
- V2 / Composition Engine: роли, группы, связи, сигналы, предложения.
- V3 / Navigation Engine: вкладки, страницы, навигационный контекст.
- P2 / Runtime: мост между V2 и V1.
- P1 / Adapter: связь движков с UI.
- Reference snapshot: база для хранения исходной авторской композиции.

Главная проблема сейчас: V2 уже видит композицию, но еще не имеет достаточно строгих законов поведения блоков и не учитывает внутреннее содержимое блока.

## Этап 1. Заморозить текущую рабочую базу

Статус: выполнено.

Что должно быть:

- git commit текущей стабильной версии;
- tag точки восстановления;
- полный `npm run check` перед изменениями;
- запрет на хаотичные правки V1 ради V2.

Критерий готовности:

- есть commit/tag;
- safety-system проходит;
- можно откатиться.

## Этап 2. Ввести профили поведения блоков

Задача: научить V2 понимать, что разные блоки живут по разным законам.

Нужно добавить слой:

```text
composition-engine/behavior/
  compositionBehaviorProfiles.js
  resolveBlockBehaviorProfile.js
  validateBlockBehaviorProfile.js
  index.js
```

Профиль должен описывать:

- роль блока;
- допустимые края;
- желательную зону;
- минимальные размеры;
- можно ли сжимать;
- можно ли переносить;
- можно ли складывать;
- можно ли отрывать от группы;
- приоритет;
- fallback-сценарии.

Минимальные роли:

- `header`;
- `content`;
- `sidebar`;
- `control`;
- `warning`;
- `unknown`.

Критерий готовности:

- каждый блок получает профиль;
- неизвестные блоки получают осторожный профиль `unknown`;
- V2 больше не относится ко всем блокам одинаково.

## Этап 3. Расширить reference map

Задача: хранить не только координаты, но и авторский замысел.

Reference map должна содержать:

- исходные координаты;
- исходный профиль рабочей области;
- роль блока;
- тип блока;
- группу;
- связи;
- anchors;
- edge distances;
- минимальные размеры;
- порядок в группе;
- признак внутренней рабочей области;
- источник данных: пользователь, adapter, host-проект.

Важно:

```text
reference map нельзя перезаписывать адаптированной раскладкой
```

Критерий готовности:

- при сжатии V2 считает от исходного снимка;
- при расширении блоки могут восстановиться;
- авторская композиция не теряется после нескольких адаптаций.

## Этап 4. Ввести минимальные размеры блоков

Задача: запретить сжатие блоков до бессмысленного состояния.

Пока V4 не готов, минимальные размеры можно брать из:

- профиля роли;
- ручного описания блока;
- эвристики по типу блока;
- будущего поля `contentMinSize`.

Пример:

```text
header  -> minH: 2, minW: workspace
sidebar -> minW: 4, minH: 8
content -> minW: 8, minH: 6
control -> minW: 4, minH: 3
warning -> minW: 4, minH: 3
```

Критерий готовности:

- V2 не уменьшает блок ниже минимума;
- если блок не помещается, V2 ищет другой сценарий;
- V1 не получает заведомо мусорные кандидаты.

## Этап 5. Сделать цепочку кандидатов V2

Задача: V2 должен предлагать не один вариант, а несколько безопасных сценариев.

Порядок попыток:

1. сохранить исходную композицию;
2. уменьшить зазоры;
3. сжать блоки до разрешенного минимума;
4. сдвинуть блоки внутри своих зон;
5. перестроить группы;
6. сложить блоки в колонку;
7. перенести sidebar/control/warning по fallback;
8. вернуть честный отказ.

Каждый кандидат должен идти через runtime:

```text
V2 candidate -> runtime -> V1 check -> accepted/rejected
```

Критерий готовности:

- если V1 отклонил первый вариант, V2 пробует следующий;
- adapter применяет только принятый runtime результат;
- при невозможности адаптации система сообщает понятный отказ.

## Этап 6. Укрепить группы и связи

Задача: сохранить композицию, а не просто расставить блоки без пересечений.

V2 должен учитывать:

- блоки одной группы;
- порядок внутри группы;
- смысловую связку `control -> content`;
- связку `warning -> problem area`;
- связку `sidebar -> workspace edge`;
- связку `header -> full width/top`.

Критерий готовности:

- связанные блоки не разлетаются случайно;
- группа может перестраиваться, но не теряет порядок;
- V2 объясняет, почему блок перенесен.

## Этап 7. Подготовить V4 contract

Задача: не строить весь V4 сразу, но подготовить место для него.

Нужен контракт:

```text
contentSchema
innerWorkspace
contentMinSize
contentPreferredSize
contentBehavior
contentFallbacks
```

V4 в будущем должен сообщать:

- минимальную ширину;
- минимальную высоту;
- желательный размер;
- можно ли уменьшать шрифт;
- можно ли переносить элементы;
- можно ли скрывать второстепенное;
- можно ли включить внутреннюю прокрутку;
- можно ли перейти в compact-режим.

Критерий готовности:

- V2 уже умеет принимать ограничения содержимого;
- пока V4 не готов, ограничения можно задавать вручную или профилем;
- будущий V4 подключится без переписывания V2.

## Этап 8. Подключить визуальную диагностику

Задача: видеть, почему V2 принял решение.

В тестовом UI нужно показывать:

- роль блока;
- группу;
- anchors;
- min size;
- выбранный сценарий адаптации;
- причину отказа;
- связь с другими блоками;
- источник ограничения: V2 profile или будущий V4 content.

Критерий готовности:

- по кнопке `v2 info` видно не только диагноз, но и ожидаемое поведение;
- на блоке не должно быть каши из текста;
- подробности можно раскрывать отдельно.

## Этап 9. Safety-system

Задача: не дать архитектуре снова расползтись.

Нужно добавить проверки:

- V2 не импортируется в V1;
- V4 не импортируется в V1;
- runtime остается единственным мостом применения кандидатов;
- reference map не перезаписывается projection-раскладкой;
- behavior profiles имеют index/facade/tests;
- V2 candidate всегда проверяется через V1.

Критерий готовности:

- `npm run check` ловит нарушение слоев;
- структура V2/V4 проверяется так же строго, как V1.

## Этап 10. Минимальная рабочая цель

Первая стабильная цель не обязана быть идеальной дизайнерской адаптацией.

Нужно добиться:

- блоки не сжимаются до мусора;
- блоки не налезают друг на друга;
- блоки не уходят за границы;
- header сохраняет верхнюю роль;
- sidebar сохраняет боковую роль или переносится по понятному правилу;
- content остается главным;
- control и warning не теряют смысл;
- при расширении рабочей области композиция восстанавливается от reference map.

## Красные линии

Нельзя:

- чинить V2 через хаотичные правки V1;
- применять V2-кандидат без V1-проверки;
- считать последнюю адаптированную раскладку источником правды;
- уменьшать блок ниже внутреннего минимума;
- смешивать V2 и V4 в один бесконечный слой;
- делать правила под один конкретный сайт вместо универсальных контрактов.

## Рекомендуемый порядок ближайших задач

1. Реализовать `composition-engine/behavior`.
2. Подключить behavior profile в `resolveCompositionBlock`.
3. Добавить min size в V2 diagnostics.
4. Научить V2 запрещать сжатие ниже min size.
5. Подключить runtime-кандидаты с fallback-попытками.
6. Добавить тесты для desktop -> compact -> desktop.
7. Обновить UI-индикацию V2 без перегруза текста.
8. После стабилизации начать V4 contract.
