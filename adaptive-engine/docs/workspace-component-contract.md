# Workspace Component Contract

Этот документ фиксирует будущий архитектурный вектор.
На текущем этапе мы не реализуем полноценный компонентный слой, а продолжаем укреплять геометрию, layout, operations, selection и diagnostics.

## Главная идея

Компонент не должен попадать в `workspace` напрямую.

Сначала он должен описать себя для `adaptive-engine`, а уже движок решает:

- можно ли этот компонент разместить;
- какую область он занимает;
- какие ограничения у него есть;
- можно ли его двигать, изменять или удалять;
- как он влияет на другие области;
- какие ошибки или предупреждения нужно вернуть.

## Почему это важно

Движок должен стать не только калькулятором сетки, но и контрактом порядка для UI.

Если host-проект хочет использовать движок, он должен отдавать компоненты в понятной форме.
Это заставляет интерфейс быть единообразным: у каждого блока появляются id, область, ограничения и правила поведения.

## Текущая стадия

Сейчас движок работает с базовым layout item:

```js
{
  id: "area-id",
  x: 1,
  y: 1,
  w: 4,
  h: 3
}
```

Этот формат пока остается главным.
Он нужен для укрепления базовой геометрии:

- area;
- layout;
- operations;
- selection;
- diagnostics;
- rollback при ошибках;
- проверка границ и пересечений.

## Будущий контракт компонента

В будущем компонент может описываться шире:

```js
{
  id: "door-editor",
  type: "editor",
  area: { x: 10, y: 2, w: 16, h: 12 },
  minArea: { w: 8, h: 8 },
  maxArea: { w: 24, h: 18 },
  priority: 80,
  canMove: false,
  canResize: true,
  canDelete: false,
  behavior: "primary-tool"
}
```

Это пока не обязательный API.
Это направление, которое появится только после того, как базовые сценарии движка станут достаточно надежными.

## Принцип развития

Не добавлять компонентный слой раньше времени.

Сначала движок должен уверенно отвечать на простые вопросы:

- область валидна или нет;
- операция допустима или нет;
- почему операция невозможна;
- что изменилось;
- что осталось прежним;
- где возник конфликт;
- можно ли доверять итоговому состоянию.

Только после этого появится смысл добавлять `components/` слой.

## Возможный будущий слой

```text
adaptive-engine/
  components/
    componentErrorCodes.js
    createComponentDefinition.js
    normalizeComponentDefinition.js
    validateComponentDefinition.js
    resolveComponentDefinition.js
    index.js
```

## Правило на сейчас

Компонентный контракт зафиксирован как будущий вектор, но не входит в ближайшую реализацию.

Ближайший фокус:

1. операции;
2. ошибки операций;
3. отчеты;
4. стабильность rollback;
5. сценарии выбора;
6. сценарии поведения layout после изменений.
