# V4 Content Engine: направление

V4 - будущий слой Adaptive Engine, который отвечает за содержимое внутри блоков.

Главная идея: каждый блок является мини-рабочей областью со своей внутренней сеткой, своими элементами и своими законами адаптации.

## Зачем нужен V4

V2 может понимать, что блок является `content`, `sidebar`, `header`, `control` или `warning`. Но V2 не знает, что находится внутри блока.

Без V4 движок видит внешний прямоугольник, но не понимает:

- сколько места нужно тексту;
- можно ли переносить кнопки;
- можно ли уменьшать шрифт;
- можно ли скрыть второстепенную подпись;
- можно ли превратить строку кнопок в колонку;
- можно ли таблицу заменить списком;
- когда блок уже нельзя сжимать.

Из-за этого блок может ужаться до технически допустимого размера, но стать бесполезным для человека.

## Блок как вложенный workspace

Каждый блок должен рассматриваться как отдельная локальная рабочая область.

```text
V1: общая сетка страницы
V2: композиция блоков на странице
V4: внутренняя сетка и содержимое конкретного блока
```

Внутри блока могут быть:

- текстовые зоны;
- кнопки;
- формы;
- выпадающие списки;
- таблицы;
- карточки;
- локальные меню;
- внутренние группы;
- вложенные блоки.

## Что V4 должен отдавать V2

V4 не должен напрямую двигать внешний блок по общей сетке. Он должен сообщать V2 ограничения и возможности:

- минимальная ширина блока;
- минимальная высота блока;
- желательная ширина блока;
- желательная высота блока;
- можно ли сжимать содержимое;
- можно ли перестраивать содержимое;
- можно ли включить внутреннюю прокрутку;
- можно ли скрыть второстепенные элементы;
- можно ли перейти в компактный внутренний режим;
- критичность содержимого.

## Минимальные метрики человека

V4 должен учитывать не только математику, но и восприятие пользователя.

Базовые ориентиры:

- текст должен оставаться читаемым;
- кнопка должна оставаться нажимаемой;
- поле ввода должно оставаться пригодным для ввода;
- расстояние между интерактивными элементами не должно превращаться в кашу;
- смысловая группа внутри блока не должна разваливаться без явного fallback.

Минимальный экран смартфона можно использовать как нижнюю границу проверки. Если содержимое уже нельзя нормально прочитать или нажать, блок нельзя считать безопасно адаптированным.

## Связь V2 и V4

V2 отвечает за внешнюю композицию. V4 отвечает за внутреннее содержимое.

```text
V4: этот блок нельзя сделать уже 8 колонок
V2: тогда перестраиваю композицию вокруг этого ограничения
V1: проверяю, что итоговая геометрия допустима
runtime: разрешаю или отклоняю применение
```

Если V4 говорит, что блок нельзя сжимать дальше, V2 должен искать другой сценарий:

1. уменьшить зазоры между блоками;
2. перенести соседние блоки;
3. перестроить группу;
4. сложить блоки в колонку;
5. включить внутренний compact-режим блока;
6. вернуть честный отказ, если безопасного решения нет.

## Стоп-линия

V4 не должен появляться как хаотичный набор частных правил под конкретный сайт.

Он должен быть универсальным слоем:

- описывает содержимое;
- сообщает ограничения;
- предлагает внутренние режимы;
- не ломает V1;
- не заменяет V2;
- не знает про конкретный UI host-проекта напрямую.

## Ближайший практический шаг

До полноценного V4 нужно подготовить V2:

- добавить `contentMinSize` в поведение блоков;
- добавить признак `innerWorkspace`;
- запретить сжатие ниже минимального пользовательского размера;
- научить V2 выбирать fallback, если блок нельзя уменьшить.

Так V2 уже сейчас перестанет сжимать блоки до бесполезного состояния, а будущий V4 сможет подключиться без переделки архитектуры.
