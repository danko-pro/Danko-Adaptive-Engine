# Integration Spike Notes

Дата фиксации: 2026-05-06

Этот документ фиксирует выводы из первого переноса `adaptive-engine` в реальный калькуляторный интерфейс `admin-ui`.

Spike считается успешной проверкой идеи, но не становится основной веткой разработки. Основной фокус остается на развитии `adaptive-engine` как самостоятельного, переносимого layout-движка.

## Главный вывод

`adaptive-engine` можно встроить в существующий host-проект через отдельный adapter-слой.

Правильная формула интеграции:

```text
adapter описывает блоки
-> engine считает и валидирует layout
-> React рисует CSS Grid по engine coordinates
```

Движок не должен знать про конкретный калькулятор, его стадии, DOM-структуру, стили или компоненты. Host-проект должен сам привести свои блоки к контракту движка.

## Что подтвердил spike

- Движок можно перенести в реальный `admin-ui` без переноса донорского React-приложения.
- Публичный вход должен идти через `adaptive-engine/core/index.js`.
- Adapter-слой нужен обязательно: он отделяет модель калькулятора от модели движка.
- `probe` и `sandbox` полезны как проверочный слой, но не являются финальной интеграцией.
- Sandbox drag может отправлять операции в `applyOperation`, а движок может принимать или отклонять результат.
- Calibration matrix полезна для проверки разных размеров workspace.
- Stage matrix полезна для проверки разных сценариев калькулятора.

## Правильный визуальный принцип

Движок должен отдавать координаты сетки:

```js
{ x, y, w, h }
```

UI должен рисовать их через CSS Grid:

```tsx
gridColumn: `${item.x} / span ${item.w}`
gridRow: `${item.y} / span ${item.h}`
```

Это важнее, чем пытаться вручную повторить геометрию через абсолютные координаты.

## Неправильный путь

Не использовать `absolute left/top` как основной layout-принцип для интеграции с движком.

Такой подход быстро расходится с реальной сеткой:

- сложнее держать геометрию ячейки;
- легче получить смещение;
- сложнее поддерживать resize;
- труднее объяснять ошибки;
- UI начинает дублировать работу движка.

Абсолютные координаты можно использовать только как вспомогательную диагностику или preview, но не как основную модель layout.

## Что пока не делаем

На текущем этапе не нужно углубляться в подгонку калькулятора.

Отложено:

- разметка всех реальных секций через `data-layout-block`;
- полноценный apply-mode;
- управление реальными блоками калькулятора;
- калибровка конкретной stage;
- Playwright visual smoke для всех viewport;
- исправление конкретного mobile layout калькулятора;
- сохранение sandbox drag в storage.

Эти задачи относятся к следующему этапу интеграции калькулятора, а не к развитию ядра прямо сейчас.

## Что это меняет для движка

Spike показал, что движку нужны не калькуляторные костыли, а зрелые универсальные контракты.

Приоритеты для `adaptive-engine`:

- стабильный публичный API через `core/index.js`;
- единый формат ошибок и отказов;
- понятные diagnostics reports;
- строгий operation pipeline;
- независимые assistant-слои;
- безопасное strict-поведение по умолчанию;
- возможность работы от host workspace object, а не только от browser observer;
- отчеты, которые host-проект может показать человеку.

Движок не должен:

- импортировать UI;
- знать про калькулятор;
- зависеть от CSS конкретного host-проекта;
- автоматически переставлять блоки без явно включенного режима;
- молча исправлять ошибки layout.

## Текущий архитектурный вектор

Развивать нужно сам движок, а не конкретную раскладку калькулятора.

Ближайший фокус:

```text
operations
-> rejections
-> constraints
-> diagnostics
-> behavior modes
```

Смысл:

- `operations` принимают намерение изменить layout;
- `rejections` объясняют, почему действие запрещено;
- `constraints` задают ограничения блоков;
- `diagnostics` собирают состояние движка в понятный отчет;
- будущие behavior modes определят, как действовать после отказа.

## Поведение по умолчанию

Базовый режим движка должен оставаться строгим:

```text
valid operation -> применить
invalid operation -> вернуть отказ
layout -> не менять
```

`suggest` и `auto` можно добавлять позже, но они должны быть отдельными режимами поверх strict core.

## Роль калькуляторного spike

Калькуляторный spike остается источником уроков.

Он доказал:

- идея переносима;
- adapter обязателен;
- CSS Grid является правильной визуальной моделью;
- host-проект должен приводить свои блоки к контракту движка;
- движку нужны сильные отчеты и объяснимые отказы.

Но spike не должен перетянуть roadmap на себя. Основная рабочая база сейчас - текущий проект `adaptive-engine`.

## Правило для следующих шагов

Если новая задача касается конкретного калькулятора, сначала спросить:

```text
Это улучшает универсальный adaptive-engine?
Или это локальная подгонка admin-ui?
```

Если задача локальная для калькулятора, она должна идти в adapter/probe/CSS host-проекта.

Если задача улучшает универсальную модель layout, ошибок, операций, ограничений или diagnostics, она должна идти в `adaptive-engine`.
