# V2 decision log

Дата фиксации: 2026-05-11.

Этот документ не является финальной спецификацией. Это рабочий журнал решений по V2, чтобы не терять контекст между сессиями, тестами и правками.

## Текущий подтвержденный результат

После последних правок V2 стал заметно стабильнее:

- широкая авторская карта больше не портится после сжатия;
- при возврате на широкий экран блоки снова раскладываются близко к исходной композиции;
- блоки от края до края V2 держит лучше;
- блоки уже не сжимаются в совсем абсурдные размеры так легко, как раньше;
- V2 уже видит роли, группы, связи, состояния, сигналы и предложения.

При этом V2 еще не завершен:

- он все еще часто раскладывает блоки как прямоугольники без столкновения, а не как осознанные композиционные группы;
- `content`-блоки стали лучше, но группы вида "это один ряд", "это смысловой кластер", "это авторская композиция" пока недостаточно управляют раскладкой;
- `sidebar`, `warning`, `control` нуждаются в более жестких личных правилах;
- на узких экранах V2 должен не просто вписать блоки, а выбрать понятный fallback-сценарий.

## Главный закон на ближайший этап

V2 должен учиться не только вмещать, а компоновать.

Порядок принятия решения:

```text
reference map
-> роли и связи блоков
-> группы и авторские кластеры
-> допустимые сценарии поведения
-> кандидат V2
-> проверка V1
-> применение через adapter/runtime
```

V2 не должен адаптировать сцену от последней временной адаптированной версии. Источником правды остается авторская карта.

## Групповое поведение важнее одиночной подгонки

Следующий правильный шаг - встроить в V2 групповое поведение.

V2 должен сначала понять:

- вот это авторская строка;
- вот это боковая зона;
- вот это служебный блок;
- вот это предупреждение относится к конкретному блоку;
- вот это главный смысловой блок;
- вот эти блоки образуют один кластер.

И только потом решать:

- сжимать;
- переносить;
- складывать;
- превращать в overlay;
- оставлять на месте;
- отклонять действие.

## Ролевые решения

### Header

`header` и full-width/band-блоки считаются каркасом.

Они должны:

- держать верхнюю или нижнюю роль;
- не превращаться случайно в центральный блок;
- сохранять привязку к ширине рабочей области, если были созданы как каркас.

### Sidebar

`sidebar` получает отдельные режимы:

- `static` - занимает место в сетке;
- `overlay` - выходит поверх контента и не занимает место в основном потоке;
- `stack` - переносится в колонку или отдельную секцию;
- `collapsed` - превращается в компактный триггер/кнопку.

Статичный sidebar обязан занимать указанную область. Overlay/collapsed sidebar может быть поверх остальных блоков, но это должно быть явно отражено в состоянии V2.

### Content

`content` является главным смысловым блоком.

Правила:

- не уменьшать ниже минимального размера содержимого;
- сохранять центральную или основную смысловую роль;
- если content-блоков несколько, учитывать их группу и порядок;
- не считать каждый content-блок независимым прямоугольником, если он входит в авторскую композицию.

### Warning и Control

`warning` и `control` не должны жить как полностью случайные блоки.

Они должны быть привязаны:

- к ближайшему смысловому блоку;
- к группе;
- к зоне;
- или к явной зависимости, созданной adapter/UI.

Если связи нет, V2 имеет право выдать рекомендацию: блоку нужна зависимость или описание поведения.

## Решение по привязкам блоков

Идея принята: связанные блоки нужны.

Пример: пользователь выбирает блок и создает рядом `warning` "Опасность". Такой блок должен появиться не просто в свободной ячейке, а как связанный с исходным блоком.

Граница ответственности:

- UI/adapter создает действие и записывает связь;
- V2 читает связь из контекста;
- V2 усиливает relation и учитывает ее при раскладке;
- V2 не должен напрямую создавать UI-элементы и не должен знать про React.

Минимальный путь внедрения:

1. Добавить запись зависимости в данные блока или отдельный список dependencies.
2. Протянуть dependency из adapter в composition context.
3. Научить UI-команду создавать связанный `warning` или `control` от выбранного блока.
4. Добавить тест: V2 видит связанную пару и не раскладывает ее как два случайных блока.

### Фиксация 2026-05-16

`dependencies` становится официальным минимальным каналом явной связи для V2.

Граница слоев:

- блок может хранить связь в `meta.dependencies`, `meta.dependsOn` или `meta.linkedTo`;
- debug/UI собирает эти связи из блоков;
- adapter передает их в `evaluateCompositionPlanCommand` и `applyCompositionFixCommand`;
- runtime передает их дальше в `resolveCompositionPlan`;
- V2 усиливает relation до `strong`, если dependency явно указывает на целевой блок.

Это не означает, что V2 уже умеет идеально перестраивать связанную группу. Это означает, что он больше не обязан угадывать связь только по расстоянию.

Стоп-линия: не дублировать dependency-логику в разных местах. Если нужна новая привязка, она должна пройти через этот канал или через следующий формальный канал `relationships`.

## Runtime и отказ V1

Если V1 отклонил кандидат V2, система не должна ломаться.

Правильный путь:

```text
V2 предлагает кандидат
runtime проверяет его через V1
V1 говорит "нет"
runtime не применяет кандидат
V2 пробует другой сценарий
если безопасного сценария нет, сцена остается стабильной
```

Нельзя:

- применять кандидат силой;
- перезаписывать author/reference map временной проекцией;
- делать вид, что ошибка V1 является успехом V2;
- чинить одну коллизию разрушением всей композиции.

Перед изменением V2, adapter или runtime нужно фиксировать:

- какую проблему решаем;
- какой слой отвечает за решение;
- какие данные должны пройти через границу слоев;
- что считается успешным тестом;
- какой fallback должен сработать при отказе V1;
- какие сценарии пока сознательно не реализуем.

## Ближайшие задачи

1. Укрепить групповое поведение V2.
2. Добавить явные dependencies для связанных блоков.
3. Разделить author/reference map и временные V2 projections.
4. Усилить правила `sidebar`, `warning`, `control`.
5. Добавить тесты на связи и отказ V1.
6. Продолжить калибровку auto-режима только через проверяемые маленькие шаги.

## Стоп-линии

- Не менять V1 ради удобства V2.
- Не добавлять скрытое поведение без отчета в UI.
- Не считать "геометрически влезло" равным "композиционно правильно".
- Не перезаписывать исходную авторскую композицию автоадаптацией.
- Не добавлять новую умность V2 без теста или хотя бы явной проверочной визуализации.

## Связанные служебные блоки

V2 не должен сам создавать служебные UI-блоки. Создание `warning` и `control` остается действием UI/adapter-слоя, потому что только host-интерфейс знает, что именно выбрал пользователь и где это действие должно появиться.

Правильный путь:

```text
пользователь выбирает блок
UI вызывает действие "создать связанную опасность" или "создать связанный контроль"
adapter создает новый блок через обычное создание area
adapter записывает связь в meta.dependencies
V2 читает dependency и усиливает смысловую связь
runtime/V1 проверяет итоговую геометрию
```

Граница ответственности:

- UI отвечает за жест пользователя и меню действий;
- adapter отвечает за создание блока и запись `meta.dependencies`;
- V2 отвечает за чтение связи и учет ее в композиции;
- runtime отвечает за безопасную проверку кандидата;
- V1 не должен знать, почему блоки связаны, он проверяет только допустимость операции.

Минимальный формат связи:

```js
meta: {
  dependencies: ["source-block-id"]
}
```

Это решение не заменяет будущие `relationships`. `dependencies` остается простым каналом явной связи, а `relationships` позже сможет описывать более богатые отношения: владелец, группа, роль, порядок, предпочтительный fallback.
