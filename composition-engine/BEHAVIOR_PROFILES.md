# V2: Reference Map и профили поведения блоков

Этот документ фиксирует следующий важный шаг V2: композиция должна опираться не только на координаты, а на смысл блоков, их роли, связи и исходный авторский замысел.

## Почему координат недостаточно

Координаты `x`, `y`, `w`, `h` говорят, где блок стоит сейчас. Но они не говорят, зачем он там стоит.

Для адаптации этого мало. Один и тот же прямоугольник может быть:

- сайдбаром;
- главным контентом;
- верхним меню;
- предупреждением;
- служебным контролом;
- частью группы;
- временным блоком без роли.

Если V2 видит только координаты, он может аккуратно вписать блок в сетку, но разрушить композицию.

## Reference Composition Map

Reference map - это исходный снимок авторской раскладки.

Она должна сохранять не только текущие размеры блоков, но и намерение:

- исходную рабочую область;
- исходные координаты блока;
- роль блока;
- тип блока;
- привязки к краям;
- смысловую зону;
- группу;
- соседей;
- зазоры;
- минимальные размеры;
- ожидаемое поведение при сжатии;
- допустимые fallback-сценарии.

Главное правило:

```text
V2 адаптирует от reference map, а не от последней адаптированной раскладки.
```

Это защищает систему от накопления ошибок, когда сжатая версия становится новым источником правды.

## Block Behavior Profile

Профиль поведения объясняет V2, как конкретный тип блока должен вести себя при изменении рабочей области.

Минимальный состав профиля:

```text
role              -> смысловая роль блока
preferredZone     -> желаемая зона рабочей области
allowedEdges      -> допустимые края привязки
preferredAnchor   -> главная привязка
minWidth/minHeight -> минимальный безопасный размер
canResize         -> можно ли менять размер
canMove           -> можно ли переносить блок
canStack          -> можно ли складывать в колонку
canDetach         -> можно ли отрывать от исходной группы
priority          -> важность блока
fallbacks         -> список запасных сценариев
```

## Ролевые правила

### Header

`header` - верхний структурный блок.

Правила:

- сохраняет верхнюю роль;
- обычно тянется по ширине рабочей области;
- не должен случайно становиться центральным блоком;
- при сжатии может уменьшаться по высоте или перестраивать внутреннее содержимое;
- если места мало, должен сохранять навигационную или структурную функцию.

### Sidebar

`sidebar` - боковая зона.

Правила:

- должен быть привязан к одной из четырех сторон рабочей области;
- не должен плавать в случайной центральной зоне;
- при нехватке ширины может быть перенесен, свернут или сложен по сценарию;
- не должен перекрывать главный контент;
- если сайдбар важен, V2 должен явно описать, куда он переезжает.

### Content

`content` - главный смысловой блок.

Правила:

- должен оставаться главным смысловым блоком композиции;
- обычно занимает центральную или основную рабочую зону;
- не должен уменьшаться ниже минимального размера содержимого;
- второстепенные блоки должны уступать ему место;
- если контента несколько, V2 должен определить группу и порядок.

### Control

`control` - управляющий блок.

Правила:

- часто связан с конкретным content/sidebar/warning блоком;
- может переноситься рядом, ниже или внутрь связанной зоны;
- не должен терять связь с тем блоком, которым управляет;
- при сжатии может становиться компактнее, но не должен исчезать без явного fallback.

### Warning

`warning` - предупреждение, ошибка, риск или критическая зона.

Правила:

- не должен перекрывать главный контент;
- может быть рядом с проблемной областью или вынесен в отдельную зону;
- должен сохранять видимость, если ошибка важная;
- может иметь высокий приоритет в режиме диагностики.

### Unknown

`unknown` - блок без описанного смысла.

Правила:

- V2 не должен уверенно перестраивать такие блоки;
- должен просить описание роли;
- может применять только безопасные базовые сценарии: вписать, не пересекать, не выходить за границы.

## Поведение по режимам рабочей области

### Desktop

Цель: максимально сохранить авторскую композицию.

V2 должен беречь:

- расстояния;
- группы;
- порядок;
- краевые привязки;
- крупные смысловые зоны.

### Tablet

Цель: сохранить композицию, но разрешить умеренное сжатие и перенос.

Допустимо:

- уменьшать зазоры;
- перестраивать группы;
- переносить второстепенные блоки;
- сохранять главный content как приоритет.

### Compact

Цель: сохранить смысл, даже если исходная композиция уже не помещается.

Допустимо:

- складывать блоки;
- переносить sidebar;
- уменьшать второстепенные блоки;
- использовать минимальные зазоры;
- выдавать предупреждения, если смысловая композиция страдает.

### Mobile

Цель: не сохранить картинку один в один, а сохранить смысл и порядок.

Допустимо:

- строить колонку;
- сворачивать sidebar;
- переносить control под связанный content;
- показывать warning отдельно;
- использовать мобильный порядок блоков.

## Что делать, если V1 сказал "нет"

V2 не имеет права спорить с V1.

Если runtime получил отказ от V1, V2 должен попробовать следующий безопасный сценарий:

1. уменьшить зазоры;
2. уменьшить блоки до минимально допустимых размеров;
3. сдвинуть блок внутри своей зоны;
4. перестроить группу;
5. сложить блоки в колонку;
6. перенести sidebar/control/warning по fallback-правилу;
7. вернуть честный отказ, если безопасной композиции нет.

## Стоп-линии

V2 нельзя:

- применять раскладку без проверки V1;
- перезаписывать reference map адаптированной версией;
- игнорировать группы и связи;
- уменьшать content ниже его минимума;
- превращать sidebar в случайный свободный блок;
- чинить коллизию ценой разрушения смысла;
- принимать "влезло в сетку" за "композиция правильная".

## Следующий этап реализации

1. Ввести контракты профилей поведения.
2. Добавить resolver профиля по роли блока.
3. Расширить reference snapshot: роль, зона, группа, anchors, min sizes.
4. Научить V2 строить несколько кандидатов, а не один.
5. Передавать кандидатов в runtime.
6. При отказе V1 пробовать следующий сценарий.
7. Показывать в UI, почему V2 выбрал именно такой сценарий.

## Критерий успеха

V2 считается полезным, когда он не просто двигает блоки, а сохраняет композиционный смысл:

- header остается header;
- sidebar остается боковой ролью или честно переносится;
- content остается главным;
- control не теряет связь;
- warning не перекрывает важное;
- группы и порядок сохраняются настолько, насколько позволяет текущий профиль рабочей области.
