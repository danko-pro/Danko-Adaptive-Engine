# Adaptive Engine: инструкция для подготовки host-проекта

Этот файл предназначен для передачи другой нейросети или разработчику. Он описывает текущий проект, его архитектуру, границы ответственности и направление подготовки внешнего сайта к интеграции с движком.

## 1. Главная идея проекта

Проект строит переносимый адаптивный layout-движок.

Цель: дать сайту не просто набор CSS-правил, а отдельный слой, который понимает рабочую область, сетку, блоки, операции, ошибки, ограничения и в будущем сможет управлять адаптивной композицией интерфейса.

Движок не должен быть завязан на один конкретный сайт или калькулятор. Он должен подключаться к host-проекту через adapter.

Базовая формула интеграции:

```text
host UI -> adapter -> adaptive-engine -> adapter -> host UI
```

## 2. Текущая рабочая архитектура

В проекте есть несколько основных слоев.

```text
adaptive-engine/   -> V1 ядро движка
engine-adapter/    -> переносимый слой между UI и движком
src/               -> тестовый UI и debug-интерфейс
safety-system/     -> проверки, заморозка, админка безопасности
```

### adaptive-engine

Это V1 ядро. Оно отвечает за строгую геометрию и правила.

V1 умеет:

- считать параметры сетки;
- определять рабочую область;
- создавать и валидировать area;
- работать с координатами;
- проверять layout items;
- нормализовать layout;
- обнаруживать пересечения;
- выполнять операции;
- возвращать отчеты;
- возвращать ошибки и отказы;
- создавать диагностику;
- работать с ограничениями;
- работать с намерениями;
- строить снимок движка;
- проверяться через safety-system.

V1 не должен знать про React, браузер, конкретный сайт, калькулятор или визуальные компоненты.

### engine-adapter

Adapter переводит действия UI в язык движка.

Он отвечает за:

- перевод pointer/click в ячейку сетки;
- выбор ячейки или блока;
- создание area из ячейки или выделенной области;
- движение блока;
- resize блока;
- rename/copy/delete;
- применение операций движка;
- перевод ошибок и отказов в понятный UI-ответ;
- временную защитную проекцию блоков при изменении размера сетки;
- границу передачи управления будущему V2.

Adapter не должен рисовать интерфейс и не должен зависеть от React.

### src

Это тестовый UI.

Он нужен, чтобы руками проверять:

- выделение ячеек;
- создание блоков;
- движение блоков;
- resize;
- rename/copy/delete;
- отображение ошибок;
- реакцию сетки на изменение размеров workspace;
- работу adapter-команд.

Этот слой не является финальной архитектурой host-проекта.

### safety-system

Это система безопасности проекта.

Она проверяет:

- границы импортов;
- структуру движка;
- заморозку V1;
- guardrails против случайного смешивания V1 и V2;
- тесты всех слоев;
- сборку тестового UI.

Запуск:

```bash
npm run check
```

## 3. Что такое V1

V1 - это строгий layout kernel.

Его задача не “красиво все переставить”, а надежно отвечать:

- область валидна или нет;
- операция возможна или нет;
- почему операция невозможна;
- что изменилось;
- где конфликт;
- какие координаты допустимы;
- находится ли блок внутри сетки;
- пересекается ли блок с другим блоком.

V1 должен быть скучным, строгим и надежным.

V1 не должен заниматься умной адаптацией смысла интерфейса.

## 4. Что уже важно для host-проекта

Host-проект должен готовиться не к хаотичному CSS, а к работе через контракт.

У каждого управляемого блока должны появиться:

- стабильный `id`;
- тип блока;
- область размещения;
- правила минимального размера;
- правила изменения размера;
- информация, можно ли блок двигать;
- информация, можно ли блок удалять;
- информация, можно ли блок копировать;
- данные для отображения;
- понятное имя для человека;
- связь с внутренними элементами.

Минимальный текущий формат layout item:

```js
{
  id: "block-id",
  x: 1,
  y: 1,
  w: 4,
  h: 3
}
```

В будущем этот формат может быть расширен, но host уже сейчас должен отделять геометрию от визуального CSS.

## 5. Правильная подготовка компонентов сайта

Компоненты host-сайта нужно постепенно привести к единой системе.

### Компонент не должен сам решать все

Плохо:

```text
Компонент сам хранит координаты, сам двигается, сам адаптируется, сам скрывается.
```

Хорошо:

```text
Компонент описывает себя.
Adapter передает описание движку.
Движок проверяет.
UI отображает результат.
```

### Разделить данные, геометрию и отображение

Для каждого блока желательно разделять:

- данные блока;
- layout-описание блока;
- visual component;
- adapter mapping;
- правила поведения.

Пример:

```js
{
  id: "price-summary",
  type: "summary-card",
  title: "Итого",
  layout: { x: 1, y: 1, w: 12, h: 6 },
  dataKey: "estimate.summary",
  capabilities: {
    movable: true,
    resizable: true,
    deletable: false
  }
}
```

## 6. Что такое adapter для host-проекта

Adapter - это не UI-компонент.

Adapter должен уметь:

- взять реальные блоки сайта;
- превратить их в items для движка;
- вызвать операции движка;
- получить результат;
- вернуть данные обратно UI;
- показать ошибку человеку;
- не дать UI попасть в невалидное состояние.

Host-проекту нужен свой adapter mapping:

```text
host component -> engine item
engine result -> host state
engine rejection -> user message
```

## 7. Что такое V2 в будущей архитектуре

V2 не должен быть просто “более умной подгонкой”.

V2 должен стать слоем композиции.

Если V1 отвечает за область, то V2 отвечает за смысл и поведение областей.

V2 должен смотреть на блоки как на рабочие области, внутри которых может жить содержимое:

- текст;
- кнопка;
- форма;
- список;
- таблица;
- карточка;
- группа элементов;
- вложенная сетка.

V2 должен уметь рассуждать:

- как блоки связаны между собой;
- как их расположить на desktop;
- как их расположить на tablet;
- как их расположить на mobile;
- когда блоки должны стать колонкой;
- когда текст должен уменьшиться;
- когда кнопки должны растянуться;
- когда содержимое нужно скрыть или свернуть;
- какие блоки нельзя разрывать.

## 8. Граница V1 и V2

V1 и V2 не должны одновременно управлять поведением блоков.

Текущая граница передачи находится в `engine-adapter`.

Режимы:

```text
off     -> ничего не применять автоматически
safe    -> adapter использует старую защитную V1-проекцию
suggest -> V2 может предложить решение, но не применяет его сам
auto    -> V2 может вернуть применяемое решение
```

Контракт находится здесь:

```text
engine-adapter/contracts/adapterBehaviorModes.js
```

Правило:

```text
Если V2 активен, adapter не должен параллельно применять V1-проекцию.
```

Иначе два слоя начнут спорить за координаты.

## 9. Как host-проекту готовиться к V2

Host-проекту не нужно сразу строить V2.

Но уже сейчас нужно готовить компоненты так, чтобы V2 потом мог их понять.

### Нужно подготовить ElementSchema

Каждый значимый элемент должен описывать себя:

```js
{
  id: "submit-button",
  type: "button",
  role: "primary-action",
  label: "Сохранить",
  minSize: { w: 3, h: 1 },
  behavior: {
    mobile: "full-width",
    desktop: "inline"
  }
}
```

### Нужно подготовить ElementRegistry

Нужно место, где перечислены управляемые типы:

```text
button
input
select
card
summary
table
toolbar
section
```

### Нужно подготовить ComponentSchema

Блок должен описывать не только свою геометрию, но и внутренний состав:

```js
{
  id: "client-form",
  type: "form-block",
  layout: { x: 1, y: 1, w: 16, h: 10 },
  children: [
    { id: "client-name", type: "input" },
    { id: "client-phone", type: "input" },
    { id: "save-client", type: "button" }
  ]
}
```

### Нужно подготовить данные отдельно от UI

Не стоит держать смысл только в JSX/HTML.

Лучше иметь понятный слой данных:

```text
данные -> схема -> adapter -> engine -> UI
```

## 10. Что не нужно делать сейчас

Не нужно:

- встраивать V2 внутрь V1;
- смешивать CSS-адаптацию сайта с логикой движка;
- позволять каждому компоненту самому решать координаты;
- делать absolute `left/top` как основу интеграции;
- переносить debug UI в production как финальный интерфейс;
- заставлять движок угадывать хаотичную структуру компонентов.

## 11. Что нужно делать сейчас

Нужно:

- укреплять V1;
- держать adapter чистым;
- готовить host-компоненты к описательному контракту;
- отделять визуальный компонент от layout-данных;
- заводить стабильные id;
- описывать возможности блоков;
- описывать внутренние элементы блоков;
- документировать связи между блоками;
- готовить будущий ElementRegistry;
- готовить будущий ComponentRegistry;
- проверять интеграцию через adapter, а не напрямую.

## 12. Как должен выглядеть путь интеграции

Правильный путь:

```text
1. Host описывает блоки.
2. Adapter переводит блоки в items.
3. V1 проверяет геометрию.
4. UI отображает проверенный layout.
5. Пользователь делает действие.
6. Adapter переводит действие в operation.
7. V1 принимает или отклоняет operation.
8. UI применяет результат или показывает ошибку.
9. В будущем V2 подключается между adapter и V1 как слой композиции.
```

## 13. Как готовить существующий сайт

Если сайт уже существует, его не нужно переписывать сразу.

Лучше двигаться по шагам:

1. Найти основные блоки интерфейса.
2. Дать каждому блоку стабильный id.
3. Вынести описание блока в данные.
4. Отделить layout от CSS.
5. Описать минимальные размеры.
6. Описать действия, которые разрешены блоку.
7. Описать внутренние элементы блока.
8. Сделать adapter mapping.
9. Подключить V1 только к ограниченной рабочей области.
10. Проверить операции.
11. Только после этого думать о V2-композиции.

## 14. Главная архитектурная мысль

Движок не должен становиться сайтом.

Сайт не должен сам становиться движком.

Между ними должен быть adapter.

V1 отвечает за строгую валидную геометрию.

V2 в будущем будет отвечать за адаптивную композицию и внутреннее поведение блоков.

Host-проект должен готовить компоненты так, чтобы они были понятны движку:

```text
понятный id
понятный тип
понятная геометрия
понятные данные
понятные возможности
понятные внутренние элементы
понятные связи
```

Тогда движок сможет не угадывать интерфейс, а работать с ним как с системой.

## 15. Текущее состояние

На текущем этапе:

- V1 работает и заморожен safety-system;
- adapter вынесен отдельно от UI;
- тестовый UI позволяет руками проверять операции;
- защитная adapter-проекция удерживает блоки в рабочей области при изменении размера;
- V2 не реализован;
- граница V1/V2 зафиксирована;
- направление V2 как слоя композиции зафиксировано.

Следующий правильный шаг для host-проекта: подготовить компоненты к контракту, а не пытаться сразу встроить всю автоматику.
